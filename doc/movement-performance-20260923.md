# 持续行走卡顿：2026-09-23

用户报告：iPhone 的 AlterU 内，初始流畅，持续走动约 5 秒开始卡。当前版本确实使用 RPGJS + CanvasEngine + PixiJS；之前通关与短步态验证不等于持续性能验证。

## 已确认问题与修正

1. `audio.ts` 每个脚步 `new Audio()`，旧 pool 只保留最新六个引用，并未复用播放器。按 108 世界单位/秒、25 单位一次脚步，每秒创建约 4.3 个音频对象。音乐播放失败重试也会重复创建播放器/visibilitychange监听。修正为音乐单实例、事件监听单次注册，短音效固定上限：step 3 / paper 2 / door 1，停止/结束对象优先复用。
2. NPC 静止时仍每帧 teleport + syncChanges。改为位置、方向、姿态实际变化时才更新相应信号与同步。
3. 相机和互动标记每帧改 top/left。改为同坐标的 transform 平移，并在值变化时才写入；世界比例、镜头偏移公式与碰撞不变。

4. 触屏摇杆每次pointermove触发App层setState，重复渲染整套HUD/互动树。改为ref保存旋钮与pointerdown时的边界，pointermove只更新旋钮transform和移动输入；release/cancel/lostcapture恢复原位。

## 证据及边界

- `_qa/audio-pool.test.ts`：旧实现连续1000脚步+交互/音乐失败重试，创建1155个播放器；新实现不超过7个（含音乐）且只注册一次visibilitychange监听。
- `_qa/movement-soak.mjs`：独立Chrome、390×844、DPR3、CPU4倍减速，持续往返而不是停在墙边；自然GC模式，不手工回收掩盖增长。逐段记录帧间隔/实际路程/队列/DOM/内存/布局。
- 旧实现约103秒：节点由257升至923后回落，生命周期观察者69升至402后回落；第11段最大帧间隔233ms，累计布局6272次。内存能回收，因此不把它定性为永久泄漏。
- 初始无减速/手工GC对照始终流畅，正说明短测或强制GC不能代表手机持续表现。
- 新实现同条件复测数据及触屏测试见后续记录。

这是已确认资源分配和布局开销的修复。桌面Chromium CPU降速不是iPhone WKWebView；尚不能证明用户设备约5秒卡顿已完全根治，需已发布版本同设备复验。

同条件开发构建复测：约103秒，节点保持190–191，生命周期观察者固定36；布局121次，较旧版6272次减少约98%。仍有一次83ms停顿；不以此宣称无长帧。
